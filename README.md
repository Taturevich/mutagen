# MutationFramework

A .NET 11 mutation-testing MVP using Roslyn-generated mutation schemata and NUnit through the supported `dotnet test`/VSTest interface. The CLI and SDK call the same engine. Source projects are copied into a temporary session before rewriting; source files in the checkout are not modified.

## Run the sample

```powershell
dotnet restore MutationFramework.slnx
dotnet build MutationFramework.slnx --no-restore
dotnet test samples/SampleApplication.Tests/SampleApplication.Tests.csproj --no-build --no-restore
dotnet run --project src/MutationFramework.Cli -- run --project samples/SampleApplication/SampleApplication.csproj --tests samples/SampleApplication.Tests/SampleApplication.Tests.csproj --workers 4 --output mutation-results --report json,html
dotnet run --project samples/SdkSample
```

The CLI also accepts `discover`, `plan`, and `report`. `discover` evaluates mutation candidates and uses structured VSTest discovery without executing tests. `plan` builds the instrumented projects and collects baseline coverage, but does not execute mutants. `run` executes the plan, and `report` summarizes an existing JSON report without rerunning tests. The engine uses the supported VSTest TranslationLayer API and exact discovered test case IDs. A persistent controller is kept per bounded worker. `--test-host-isolation per-test|per-mutant|per-batch|per-resource-group` selects a fresh host per test, one VSTest run in a fresh host for the covered tests of one mutant (the default), one VSTest run for a batch of coverage-disjoint mutants, or serialized batches split across declared independent resource groups. Per-mutant mode follows the normal grouped test-run model; when tests declare resource locks, supported NUnit cases are serialized in the shared mutant host while the full lock set is held. Executors that cannot enforce serialization fall back to per-test hosts. Per-batch mode requires `--execution-mode batched`, complete per-test coverage, and an explicit caller assertion that tests in each batch remain equivalent in one process. Per-resource-group mode also requires batched execution, complete coverage, a lock for every selected test, and an explicit caller assertion that lock-disjoint groups are process-isolation equivalent. Tests connected by overlapping locks stay in one group and run serially in one host; groups run in separate hosts, while mutants covered across groups remain in a single locked work unit. Both batched policies require the NUnit VSTest executor so Mutagen can enforce in-host serialization. Resource locks are held for the full execution unit. Reuse policies leave fixture, static state, database, and external-service reset to the test suite. `--execution-mode isolated|batched|auto` chooses singleton work units, coverage-conflict batches, or the safest available plan; SDK callers set `MutationOptions.ExecutionMode`. `--mutators id[,id]` selects registered mutators; SDK callers set `MutationOptions.Mutators`. `--cache DIR` selects content-addressed caching for project evaluation, mutation discovery, compilation outputs, test discovery, coverage maps, and (opt-in) validated mutation results; SDK callers set `MutationOptions.CacheDirectory`. `--mutation-result-cache-scope KEY` enables conservative result reuse when its external-state attestation remains valid. `--resource-locks testId=>lock[,lock];testId=>lock` serializes tests that declare the same external resource key; use the test IDs returned by `discover`. `--project` selects the primary production project, `--projects` adds production roots, and `--tests` accepts one or more test projects. Other options include `--framework`, `--workers`, `--output`, `--report`, `--timeout`, `--filter`, `--include`, and `--exclude`. CLI exit codes are 0 completed, 2 invalid configuration, 3 baseline failure, 4 infrastructure/engine error, and 5 canceled/incomplete.

The output directory contains `mutation-report.json` and `index.html`. JSON reports use `ReportSchemaVersion` 4 and contain per-test coverage status and covered site IDs, stable mutation IDs, test identities, execution profiles, the executable plan and responsible-mutant mapping, phase timings, process/execution counters, diagnostics, supported-mutant outcomes, and a separate `UnsupportedMutations` list with explicit reasons. The checked-in sample produced 27 executable candidates in the recorded Stryker comparison: 19 killed, 7 survived, 1 without coverage. The multi-project conformance fixture processes 229 candidates across two production and two test projects. Unsupported entries are excluded from the mutation score. Missing and corrupt probe artifacts fail coverage collection instead of being interpreted as empty coverage.

## Compare with Stryker.NET

The checked-in sample can be run through the official Stryker.NET 5.0.0 release for a local comparison. Install the tool from the repository root:

```powershell
dotnet tool install dotnet-stryker --tool-path .tools/stryker --version 5.0.0
```

Then run it from `samples/SampleApplication.Tests`:

```powershell
..\..\.tools\stryker\dotnet-stryker.exe --reporter Json --reporter ClearText --concurrency 4 --output ..\..\artifacts\benchmark\stryker --skip-version-check
```

The framework's sample invocation is shown above. For repeated timing comparisons, use the same machine and concurrency, give each run a separate output directory, and compare multiple runs. Candidate sets and supported operators differ between tools, so mutation scores are not a direct measure of equivalent coverage. The .NET 11 sample comparison is recorded in `workflow/CHANGELOG.md`.

The pinned Stryker.NET 5.0.0 transformation inventory is machine-readable in [`stryker-net-5.0.0-parity.json`](benchmarks/stryker-net-5.0.0-parity.json). It records all 255 documented transformation rows: 253 are currently supported and exercised by matrix-driven conformance tests; the two `\p{Alpha}` / `\P{Alpha}` regex negations are explicitly unsupported because `System.Text.RegularExpressions.Regex` rejects the `Alpha` category when constructed. Their C# string literals compile, but neither the original pattern nor the mutated pattern has valid runtime behavior on .NET, so the engine reports the reason instead of claiming an executable mutant.

## Incremental execution and cache safety

`--cache DIR` stores content-addressed artifacts independently for MSBuild project evaluation, mutation discovery, mutation-enabled compilation outputs, test discovery, per-test coverage maps, and (opt-in) validated mutation results. Cache keys include the evaluated production and test project graphs, configuration and source inputs, restored package assets, relevant test assemblies and runtime dependencies, selected target framework and test filter, environment inputs, and engine, mutator, and instrumentation versions. Cached output manifests are checked for safe paths and content integrity before reuse. Unresolved wildcard imports or missing dependency assets bypass project-related reuse, and cache hits, misses, invalidations, and bypasses appear in diagnostics.

Validated `Killed` and `Survived` results can be reused only when `--mutation-result-cache-scope KEY` is supplied, execution is isolated per mutant with per-test host isolation, baseline coverage is complete, and no resource locks are declared. The key includes the mutation identity and source/replacement, associated test identities and coverage mapping, project graph, test binaries and dependencies, package assets, environment, engine and instrumentation versions, and the caller's scope key. Baseline tests and coverage still run on every invocation. The scope key is the caller's attestation that external state affecting test behavior has not changed; change it when a database snapshot, service state, secret/configuration input, or other untracked dependency changes. Mutagen does not reset fixtures, databases, or external services. Unsafe or inconclusive cases bypass result reuse and execute the affected mutant. Leave the option unset to always execute every covered mutant.

## Current supported path and limitations

- The current path targets `net11.0`, supports multiple production roots, transitive project references, and multiple NUnit/VSTest projects. Project references and compile inputs are evaluated through MSBuild; roots are instrumented in a shared temporary workspace and each assembly contributes coverage probes. Roslyn discovery retains each project's evaluated language version and preprocessor symbols, and generated sources are available to semantic binding but excluded from mutation. External linked sources are copied into the isolated workspace and remapped in each owning cloned project based on evaluated Compile identities, including property-expanded wildcard includes declared by projects or imports under the copied solution tree. Projects and imports outside the copied tree remain unsupported and fail explicitly before source rewriting or mutation results are reported. Multi-target projects require an explicit `--framework`, and referenced multi-target projects must contain that framework.
- Registered mutators are isolated in a Roslyn-only assembly. External mutators can register explicitly and supply typed syntax applicability, semantic candidate generation, metadata, and either expression or statement replacement descriptions; the schema layer applies and activates those replacements. Built-in mutators implement binary/assignment operators, boolean literal/condition changes, unary/update changes, initializer clearing, statement and method-body removal, checked-expression removal, conditional/null-coalescing expressions, C# collection expressions, pattern operators, string transformations, LINQ and Math substitutions, and documented Regex pattern changes. The pinned Stryker.NET 5.0.0 matrix is in `benchmarks/stryker-net-5.0.0-parity.json`; it lists all 255 documented transformation rows: 253 supported and 2 explicitly unsupported. The unsupported `\\p{Alpha}` transformations use a category name rejected by the .NET Regex runtime and are reported with that reason. The latest small-fixture differential run matched all 28 non-ignored Stryker candidates, including bound user-defined and dynamic operators, checked arithmetic, and expression-tree mutations; remaining semantic exclusions are reported explicitly. Whole-return expressions use allocation-free statement-entry probes; nested ordinary expressions use lazy probes, while checked and expression-tree contexts use inline activation/site probes that preserve evaluation context.
- Discovery returns structured VSTest identities including exact parameterized case IDs. Under the default per-mutant policy, baseline coverage uses the supported per-test coverage collector in a shared baseline host where available; otherwise each baseline test runs with its configured isolation. With explicit per-batch isolation equivalence on the supported NUnit executor, an in-process collector captures and resets site hits at each test end, preserving exact per-test coverage in one serialized baseline host. The collector does not reset fixtures or external state. Mutation execution uses bounded persistent controllers; per-mutant policy sends all selected cases for one mutant to one testhost, serializing lock-bearing NUnit runs while their resource locks are held. Background work escaping a case can make attribution unreliable and requires conservative handling.
- Reports use schema version 4 and include an execution profile per test with baseline duration, covered sites, inferred fixture affinity, timeout, effective host-isolation policy (`PerTest`, `PerMutant`, `PerBatch`, `PerResourceGroup`, or `Mixed`), whether tests are serialized in a shared host, declared resource locks, and the derived resource-isolation group when selected. Resource keys are acquired in deterministic order and serialize matching work across workers. The default starts one fresh host per mutant and runs its selected tests together, matching normal grouped test-run behavior. Per-test host isolation remains available for tests that require a fresh process. Per-batch host reuse is an opt-in assertion of same-process isolation equivalence; per-batch requires complete per-test baseline coverage, uses coverage-disjoint planned batches, holds declared locks for the whole batch, and disables framework test parallelism. Per-resource-group mode additionally requires a caller assertion that separate lock-connected groups are process-isolation equivalent; missing locks are rejected, connected groups stay together, and mutants covered across groups execute in one work unit with all relevant locks held. Both batched reuse modes currently require the NUnit VSTest executor. Timeout policy is shown in each profile; after requesting VSTest cancellation, the engine force-terminates only the testhost processes launched for that run if they do not stop within two seconds. The engine does not promise to reset shared databases, external services, static state, or test fixtures.
- `workers` bounds mutation workers. The instrumented production project is compiled once per run. Batching groups mutants with disjoint test sets and maps each selected test to its single responsible mutant. Under the default per-mutant policy, selected tests for a mutant run together in one fresh host; per-batch policy can execute those coverage-disjoint mutants in one host after the caller asserts same-process equivalence. No mutation context is shared between batches.
- Runtime coverage sites are monotonic hit bits. After the first hit, the runtime now uses a volatile read instead of repeating an atomic exchange; concurrent first hits still use compare-and-set. An opt-in Roslyn-emitted microbenchmark measures the same five-site method with mutation checks but probes disabled/enabled. In one seven-sample run per revision, incremental probe overhead changed from 63.3% to 3.8%; checksums matched and a parallel-hit regression confirmed both sites remain recorded. This isolates steady-state method cost only; it is not an end-to-end suite speed claim. Raw and comparison data are under `benchmarks/results/coverage-overhead/`. In the optimized run the mutation-check-only median was 128.1 ms versus 3.2 ms uninstrumented, so the mutation guard/call path remains the dominant cost in this deliberately hot synthetic loop; the 3.8% figure isolates the incremental hit-recording path.
- Content-addressed caching covers MSBuild project evaluation, Roslyn mutation discovery, standalone test identities, mutation-enabled test compilation artifacts, coverage-map projections, and (when explicitly enabled and eligible) validated killed/survived mutation outcomes. Standalone `discover` refreshes test outputs in the project's shared `bin` directory; it does not restore cached outputs there because external builds do not participate in Mutagen's locks. Mutation-build cache keys include evaluated transitive project graphs, all source/build items and imported configuration, restored package assets and package files, target framework, SDK/runtime environment, engine version, and the exact generated mutation schema. Outputs are stored as SHA-256-addressed blobs and restored only after manifest integrity, path, and blob-hash validation; corrupt or missing blobs rebuild. Unresolved imports (including wildcard imports whose resolved file set cannot be tracked safely), missing restore inputs, or untracked generated compile sources bypass reuse; mutation-build artifacts omit PDBs to avoid retaining temporary workspace paths. Cache hits, misses, invalidations, and bypasses are reported. Coverage maps are reused only after rerunning every selected baseline test and parsing its probes; their keys include the observed runtime site IDs, stable test identity, candidate mapping, environment, and engine/instrumentation identity. This cache stores only the deterministic projection from observed runtime IDs to mutation IDs. Validated outcome reuse remains opt-in and restricted to isolated per-test execution with complete baseline coverage, no resource locks, and a caller-provided external-state scope key; all other mutant outcomes execute again.
- A candidate implicated by an attributable compiler diagnostic is marked `CompileError`, removed, and the remaining schema is rebuilt within a fixed retry bound. Unattributable or repeated project build failures stop the run. Engine integration tests cover structured identities, semantic exclusions, unique runtime IDs, probe artifact statuses, coverage, planning, failure attribution, statement-entry probes, and isolated/batched/auto outcome equivalence.
